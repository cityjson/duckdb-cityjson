# flatcitybuf 0.9.0 bump + DuckDB-Wasm build target

**Date:** 2026-08-14
**Status:** approved for autonomous execution (standing authorisation; Fable plans/reviews, Opus executes, TDD)

## 1. Context

Upstream cut `cpp-v0.9.0` ("Byte/Binary decode and optional FileInfo strings") and the
`HideBa/vcpkg` port is already at 0.9.0 (fork master `c2db56ac6e28cdb52dc5ade8a29c347b17442221`).
The user also wants WebAssembly as a build target now that the FCB dependency is pure
C++. Recon finding that reframes the wasm half: **the extension-ci-tools distribution
pipeline already builds wasm_mvp / wasm_eh / wasm_threads, and all three passed** in the
latest develop run — the full dependency set (flatcitybuf from the git registry,
flatbuffers, nlohmann-json, openssl) already compiles under `wasm32-emscripten`. What is
missing is local buildability, runtime proof, and documentation.

## 2. Part A — bump to `cpp-v0.9.0`

- `vcpkg.json`: registry `baseline` → `c2db56ac6e28cdb52dc5ade8a29c347b17442221`
  (fork already serves `flatcitybuf@0.9.0`).
- `justfile` `vendor-fcb`: tag → `cpp-v0.9.0` (and the recipe must rebuild even when
  `.vendor/src/flatcitybuf` exists at the old tag — fetch/checkout, don't skip).
- API delta to absorb: `fcb::FileInfo`'s schema-optional strings (`identifier`,
  `title`, `reference_date`, `poc_*` except the address members) changed
  `std::string` → `std::optional<std::string>`, so absent and present-but-empty
  are now distinct (matches the Rust oracle). Audit our uses of `header.info()`
  (`IndexedAttributeColumns`, `FindColumn`, `FlatCityBufCardinality`, anything in
  metadata conversion) and adapt; most metadata flows through upstream's
  `to_cityjson_metadata` and needs nothing.
- The Byte/UByte/Binary decode fix is in this release: the full path stops aborting
  on such files, and upstream's Byte-as-unsigned matches our `58ddbe4`. Shrink the
  CLAUDE.md/AGENTS.md "known upstream divergence" note to a resolved-history remark;
  the C++ T3 light-vs-full parity test now genuinely covers those types wherever a
  fixture carries them.
- Gate: full suite + both C++ harnesses green; behaviour changes only where 0.9.0
  legitimately fixed something (named in the commit message if any).

## 3. Part B — DuckDB-Wasm as a first-class target

Three deliverables, no CI changes (CI is already green there):

1. **Local wasm build**: install emsdk (pinned to the version extension-ci-tools'
   workflow uses; check `_extension_distribution.yml`) into a durable location
   (`.vendor/emsdk`, gitignored — never a scratchpad), reuse the Task-2 vcpkg
   clone or bootstrap one, and get `make wasm_mvp` producing
   `build/wasm_mvp/**/cityjson.duckdb_extension.wasm` with FCB enabled. Add a
   `just wasm` recipe wrapping env setup + the make target.
2. **Runtime smoke harness** (`test/wasm/`, env/opt-in like the other extra
   harnesses — not part of `make test`): Node + `@duckdb/duckdb-wasm`, loading the
   locally-built wasm extension, asserting: `read_cityjson` on a checked-in file;
   `read_flatcitybuf` on a checked-in `.fcb`; and (network-gated) `read_flatcitybuf`
   with bbox against the hosted 3DBAG URL — DuckDB-Wasm's VFS does HTTP range
   requests natively, which is exactly FCB's sweet spot. Known trap to probe:
   `DuckDBRangeReader` auto-loads `httpfs`, which does not exist in duckdb-wasm
   (its VFS handles http URLs itself) — if the autoload throws there, guard it
   (attempt-and-tolerate, or platform check) rather than losing remote reads in
   the browser. Custom-extension loading in duckdb-wasm may require
   `allow_unsigned_extensions` / a custom repository — the harness documents
   whatever incantation works.
3. **Docs**: CLAUDE.md/AGENTS.md + README section: wasm targets, `just wasm`, the
   smoke harness, and the httpfs/VFS nuance.

Fallback ruling if duckdb-wasm's published npm package refuses to load a custom
extension built against DuckDB v1.5.4 (version-matching of duckdb-wasm releases is
outside our control): the build target + a load-attempt harness still land, the
runtime assertions are marked expected-fail with the reason, and the limitation is
documented — the CI-built artifacts remain the distribution path either way.

## 4. Out of scope

- Publishing/hosting the wasm artifacts (CI's distribution pipeline already owns that).
- Browser-side demo pages; the Node harness is the runtime proof.
- The pre-existing CI red (Format/Tidy, Windows, macOS x86_64) — untouched by this work.

## 5. Testing & execution model

TDD where there is code (the httpfs guard, any FileInfo adaptation: red test first —
the smoke harness itself is the red test for wasm). Opus executors task-by-task,
Fable reviews each diff, commits to develop, push at the end.
