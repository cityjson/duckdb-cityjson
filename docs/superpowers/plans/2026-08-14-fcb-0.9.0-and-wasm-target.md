# flatcitybuf 0.9.0 + DuckDB-Wasm Target Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Consume flatcitybuf `cpp-v0.9.0` (registry + vendored prefix), and make the already-CI-green DuckDB-Wasm build a locally buildable, runtime-verified, documented target.

**Architecture:** Part A is a dependency bump absorbing one API change (`FileInfo` optional strings) and retiring the Byte/UByte/Binary divergence note. Part B adds no CI (wasm already builds green there): a pinned emsdk in `.vendor/emsdk`, a `just wasm` recipe around `make wasm_mvp`, and a Node `@duckdb/duckdb-wasm` smoke harness in `test/wasm/` that proves the built extension actually runs — including FCB over HTTP through duckdb-wasm's own VFS.

**Tech Stack:** C++17 DuckDB extension (duckdb v1.5.4, extension-ci-tools v1.5.4), vcpkg git registry, emscripten/emsdk, Node + `@duckdb/duckdb-wasm`.

**Spec:** `docs/superpowers/specs/2026-08-14-fcb-0.9.0-and-wasm-target-design.md`

## Global Constraints

- flatcitybuf release tag: `cpp-v0.9.0`; fork registry baseline: `c2db56ac6e28cdb52dc5ade8a29c347b17442221` (serves `flatcitybuf@0.9.0`). Local clone for reference: `/data2/hideba/flatcitybuf`.
- `FCB_WITH_CURL` stays OFF; native-build static libs keep `-DCMAKE_POSITION_INDEPENDENT_CODE=ON`.
- Durable toolchains only: `.vendor/emsdk`, `.vendor/prefix` — never a session scratchpad.
- Native gate after every code change: `cmake --build build/release --target cityjson_extension cityjson_loadable_extension duckdb unittest && make test`, plus `FCB_PREFIX="$(pwd)/.vendor/prefix" test/cpp/run_fcb_selective_tests.sh` and `run_encoder_tests.sh`. (Stale-`.so` trap: `ninja -C build/release src/libduckdb.so` fixes nlohmann-ABI link errors in the harnesses.)
- Commit per completed task on `develop`; never push (controller pushes).
- ODR traps per CLAUDE.md apply to any C++ edits.

- [ ] **Step 2: Update and harden `vendor-fcb`**

In the `justfile` recipe: tag `cpp-v0.8.1` → `cpp-v0.9.0`, and make the flatcitybuf clone tag-aware so re-runs upgrade instead of silently reusing the old checkout:


**Files:**

**Interfaces:**

- Produces: `build/wasm_mvp/extension/cityjson/cityjson.duckdb_extension.wasm` (verify exact path from the build output), consumed by Task 3's harness.

- [ ] **Step 1: Pin emsdk to CI's version**

Find the emsdk version the CI workflow uses: `grep -rn -i "emsdk\|emscripten" extension-ci-tools/.github/workflows/_extension_distribution.yml`. Install exactly that version into `.vendor/emsdk` (`git clone https://github.com/emscripten-core/emsdk .vendor/emsdk && ./emsdk install <ver> && ./emsdk activate <ver>`). If the workflow pins none, use its default (`latest` at the workflow's action version — record which resolved).

- [ ] **Step 2: Bootstrap durable vcpkg**

As in Interfaces above. Sanity: `VCPKG_TOOLCHAIN_PATH="$(pwd)/.vendor/vcpkg/scripts/buildsystems/vcpkg.cmake"` must exist.

- [ ] **Step 3: Build (this IS the red/green)**

```bash
source .vendor/emsdk/emsdk_env.sh
VCPKG_TOOLCHAIN_PATH="$(pwd)/.vendor/vcpkg/scripts/buildsystems/vcpkg.cmake" GEN=ninja make wasm_mvp
```

Expected: vcpkg builds the manifest deps for `wasm32-emscripten` (CI proves they compile; openssl is the slow one) and the build emits a `cityjson.duckdb_extension.wasm`. Diagnose failures with systematic-debugging — CI green means a local failure is environmental (record the fix in the report; if a fix needs a repo change, that's in scope).

- [ ] **Step 4: `just wasm` recipe + commit**


Document the one-time setup (emsdk install, vcpkg bootstrap) in the recipe's comment or a `wasm-setup` recipe that performs it. Commit: `build(wasm): local wasm_mvp build via pinned emsdk + .vendor vcpkg`.

**Files:**

**Interfaces:**
- Consumes: Task 2's `.wasm` artifact path.
- Produces: an opt-in harness (not in `make test`), same convention as `test/cpp/*` and the remote FCB test.

- [ ] **Step 1: Write the failing harness first**

`smoke.mjs` outline (adapt to the actual duckdb-wasm API of the pinned version — consult its README via the installed package, not memory):

```js
// 1. instantiate duckdb-wasm (Node: createWorker from the eh/mvp bundle)
// 2. db.open({ allowUnsignedExtensions: true })
// 3. conn.query(`LOAD '<abs path or file:// URL to cityjson.duckdb_extension.wasm>'`)
//    -- if LOAD-by-path is refused, register the file in the wasm FS
//    (db.registerFileBuffer) and LOAD the registered name; document what worked.
// 4. register test/data/minimal.city.json + test/data/fcb_bbox_attr.fcb via
//    registerFileBuffer, then assert:
//    - SELECT count(*) FROM read_cityjson('minimal.city.json')  == known count
//    - SELECT count(*), min(height) FROM read_flatcitybuf('fcb_bbox_attr.fcb') == oracle
//      (take oracle values from the native build: build/release/duckdb -c ...)
// 5. network-gated (env FCB_REMOTE_TEST_URL): bbox-filtered read_flatcitybuf on the
//    hosted URL — duckdb-wasm's VFS does HTTP range requests itself.
// exit non-zero on any mismatch; print PASS lines per assertion.
```

`run_wasm_smoke.sh`: checks the wasm artifact exists (points at `just wasm` if not), `npm ci` in `test/wasm`, runs `node smoke.mjs`. Run it now: expected RED (artifact loads or fails for a *specific* reason you then fix or document).

- [ ] **Step 2: Chase the failures to green**

Likely issues, in order: unsigned-extension loading (fix: `allowUnsignedExtensions`), platform/ABI mismatch between the npm duckdb-wasm release and duckdb v1.5.4 (if truly incompatible, invoke the spec §3 fallback ruling: keep the harness, mark runtime asserts expected-fail with the reason, document), and the `httpfs` autoload inside `DuckDBRangeReader` (duckdb-wasm has no separate httpfs). For that last one: if `read_flatcitybuf('<http url>')` fails ONLY because `AutoLoadExtension` throws, wrap the autoload in try/catch (TDD: the network-gated smoke assertion is the red test; native suite must stay green after the guard — the guard must not mask a genuinely missing httpfs on native, so catch narrowly and let the subsequent open fail loudly if the FS really can't do http).

- [ ] **Step 3: justfile recipe + commit**

```just

# Opt-in like the other extra harnesses; needs `just wasm` first.

    test/wasm/run_wasm_smoke.sh
```

Commit: `test(wasm): Node duckdb-wasm smoke harness for the wasm extension build` (plus the guard commit separately if one was needed: `fix(fcb): tolerate absent httpfs autoload under duckdb-wasm`).
